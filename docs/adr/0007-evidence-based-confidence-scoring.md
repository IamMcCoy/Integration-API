# ADR-0007: 근거 검증으로 신뢰도를 매기고 스테이징에 먼저 적재한다

- **상태:** Accepted
- **날짜:** 2026-08-06

## 배경

`filtering` / `extracting` / `persisting` 세 단계를 붙이면서 LLM 이 파이프라인 안으로
들어왔다. LLM 추출에는 환각이 섞인다 — 문서에 없는 파라미터를 그럴듯하게 만들어내거나,
일반적인 REST 관례로 빈칸을 메운다.

이걸 그대로 `api_definition` / `api_schema` 에 넣으면 **틀린 규격이 맞는 규격과
구분되지 않는 상태로** 운영 테이블에 앉는다. 이 테이블을 읽어 실제 장비를 호출하는
쪽에서는 그게 문서에서 온 건지 LLM 이 지어낸 건지 알 방법이 없다.

사람이 전부 검토하는 건 현실적이지 않다. 문서 하나에서 API 수십 개가 나오고 대상 문서는
18개다. 자동으로 넘길 것과 사람이 볼 것을 갈라야 하는데, 그 기준을 무엇으로 삼을지가
문제였다.

## 선택지

**A. LLM judge 를 따로 부른다.** 추출 결과와 원문 청크를 다른 프롬프트로 다시 넘겨
0~100 점을 받는다. 구현이 단순하다. 대신 API 비용이 두 배가 되고, 같은 입력에 점수가
매번 달라져 90/70 경계가 흔들린다. 판정자도 LLM 이라 환각을 환각으로 검증하는 셈이다.

**B. 추출할 때 confidence 를 같이 받는다.** 가장 싸다. 하지만 LLM 의 자기평가는 실제
정확도와 상관이 약하고, 지어낸 값에도 높은 confidence 를 붙인다.

**C. 근거 문자열을 원문과 대조한다.** 파라미터마다 `evidence` — 원문에서 글자 그대로
오려낸 줄 — 를 함께 내게 하고, 그 문자열이 실제 청크 안에 있는지 코드로 확인한다.
LLM 재호출이 없다.

적재 위치도 함께 정해야 했다.

**D. `api_definition` 에 `review_status` 컬럼을 달아 미승인 행도 같이 둔다.** 테이블이
늘지 않는다. 대신 이 테이블을 읽는 모든 곳이 필터를 걸어야 하고, 한 번이라도 빼먹으면
미검증 데이터가 운영으로 샌다.

**E. 스테이징 테이블 `api_extraction` 을 둔다.** 모든 추출이 여기 먼저 쌓이고 승인된
것만 운영 테이블로 옮긴다.

## 결정

**C + E.**

C 를 고른 결정적 이유는 **비대칭성**이다. 실재하는 파라미터는 근거를 그대로 옮기면
되지만, 지어낸 파라미터는 원문에 없는 문자열을 만들어낼 수밖에 없다. 검증이 문자열
포함 검사 한 줄로 끝나고, 결정적이며, 비용이 0 이다.

```
score = evidence 가 원문에 실재하는 파라미터 수 / 전체 파라미터 수 × 100
```

| 점수 | `review_status` | 동작 |
|---|---|---|
| ≥ 90 | `approved` | `api_definition` + `api_schema` 즉시 삽입 |
| 70 ~ 89 | `pending` | 스테이징에만 적재, 사람 승인 대기 |
| < 70 | `rejected` | 스테이징에만 적재, 사람이 보고 판단 |

임계값 둘은 `conf/ia-conf.xml` 설정으로 뺐다. "값이 하나뿐인 설정은 만들지 않는다"의
예외다 — 실제 문서를 돌려 보며 조정될 값이다.

E 를 고른 이유는 ADR-0003 의 제약 때문이기도 하다. Redis 태스크 상태는 TTL 24시간이라,
승인 대기가 하루를 넘기면 근거가 증발한다. 승인 대기분은 DB 에 있어야 한다.

`api_extraction.source_text` 에 청크 원문을 복사해 둔다. `TaskWorker._handle` 의
`finally` 가 작업이 끝나면 업로드 원본과 변환 산출물을 통째로 지우기 때문에
(ADR-0002), 여기 남기지 않으면 사람이 승인 화면에서 대조할 근거가 아무 데도 없다.

파라미터 타입은 `Literal['string','integer','number','boolean','array','object']` 로
잡아 구조화 출력에서 enum 으로 강제한다. 문서마다 다른 표기(`문자열`, `str`,
`varchar(64)`)를 후처리 매핑표로 흡수하면 문서가 늘 때마다 표도 늘어난다. 대신
원문 표기는 `raw_type` 에 남겨 길이 제한이나 날짜 형식이 사라지지 않게 한다.

## 결과

**좋아진 것**

- 운영 테이블에는 근거가 확인된 규격만 들어간다.
- 점수 산출에 API 비용이 들지 않고, 같은 입력에 항상 같은 점수가 나온다.
- `SpecScorer` 의 자체 점검이 LLM·DB·설정 없이 표준 라이브러리만으로 돈다.
- 반려된 추출도 원문과 함께 남아, 프롬프트를 고칠 때 무엇이 왜 틀렸는지 볼 수 있다.
- ADR-0003 이 감수한 "완료 작업은 TTL 후 404" 가 적재 결과에는 적용되지 않는다.

**나빠진 것 / 감수하기로 한 것**

- **의미는 맞는데 표현을 바꾼 경우 점수가 부당하게 깎인다.** LLM 이 근거를 요약하거나
  번역하면 원문에 없는 문자열이 된다. 프롬프트로 "글자 그대로" 를 강제했지만 보장은 없다.
- 파라미터가 하나도 없는 규격은 0점이다. 파라미터 없는 API 도 실재하지만, 이 파이프라인이
  얻으려던 것이 없으므로 사람이 보게 한다.
- 승인되지 않은 추출이 무기한 쌓인다. 정리 정책이 없다.
- 근거가 파라미터 이름과 같으면 인정하지 않는 가드를 뒀지만, 짧은 근거는 여전히 우연히
  매칭될 수 있다.
- 테이블이 하나 늘고, 승인 흐름을 위한 엔드포인트 3개가 늘었다.

**되돌려야 할 신호**

- `pending` 이 사람이 처리할 수 없는 속도로 쌓이면 임계값을 올리거나, 문자열 대조를
  통과 못 한 건에 한해 LLM judge 를 덧붙인다.
- 반대로 `approved` 중에서 틀린 규격이 발견되면 문자열 대조만으로는 부족하다는 뜻이다.
  그때는 A 를 병행한다.
- 파라미터 단위 조회·검색이 실제 요구가 되면 `api_schema` 의 JSON 을 `api_parameter`
  테이블로 편다. 지금은 "API 하나의 규격 전체를 읽는다" 가 유일한 소비 패턴이다.
