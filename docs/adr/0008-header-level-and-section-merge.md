# ADR-0008: 헤더는 h6 까지 경계로 삼고, 작은 섹션은 다시 합친다

- **상태:** Accepted
- **날짜:** 2026-08-06

## 배경

[ADR-0006](0006-custom-markdown-splitter.md) 에서 스플리터를 직접 구현하면서
분할 경계를 h1~h3 로 두었다. 이전 langchain 설정을 그대로 옮긴 값이고, 실제 문서를
보고 정한 게 아니었다.

`data/` 의 벤더 문서 18개로 처음 돌려보니 그 값이 틀렸다.

대상 문서는 개별 API 이름을 h5 에, 요청/응답 구분(`URL`, `Query parameters`, `Body`)을
h6 에 둔다. **우리가 필요한 정보가 전부 분할 기준 밖에 있었다.**

결과적으로 큰 문서에서 청크가 서로 구분되지 않았다. AhnLab DPX 는 124,772자를 h1~h3
기준 7개 섹션으로 나눈다 — 섹션당 평균 18,000자다. 그게 크기 기준으로 20조각 넘게
잘리는데, 20조각 전부 `h1='Chapter 2 REST API 목록'` 이라는 같은 메타데이터를 단다.
추출 LLM 이 그 청크를 볼 때 "어느 API 의 파라미터인가" 에 대한 단서가 0이다.

## 선택지

18개 문서 전부에 세 설정을 돌려 실측했다.
→ [실험](../experiments/2026-08-06-header-level-and-chunk-merge.md)

**A. h1~h3 유지.** 청크 2,390개. 파편은 적지만 같은 헤더 경로를 공유하는 청크가
최대 205개까지 뭉친다(WAPPLES). 큰 문서일수록 나빠진다.

**B. h1~h6 를 전부 경계로.** 군집은 1,234 → 298 로 풀리지만 청크가 4,420개(+85%)가 되고,
50자 미만 파편이 59 → 765 개로 13배가 된다. 선별 단계가 청크마다 LLM 을 부르므로
파편 하나가 곧 호출 하나다. AhnLab TrusGuard 는 470청크 중 183개(39%)가 파편이었다.

**C. h1~h6 를 경계로 삼되, `chunk_size` 에 못 미치는 인접 섹션은 이어 붙인다.**

| 지표 | A | B | C |
|---|---|---|---|
| 총 청크 (= LLM 호출) | 2,390 | 4,420 | **2,504** (+5%) |
| 50자 미만 파편 | 59 | 765 | **68** (+9) |
| 최대 군집 합 | 1,234 | 298 | **278** (−77%) |
| 상한 초과 | 0 | 0 | **0** |

## 결정

**C.**

핵심은 **헤더를 경계로 인식하는 것과 그 경계마다 청크를 끊는 것은 별개** 라는 점이다.
헤더는 전부 잡아 경로를 기록하되, 상한에 못 미치는 인접 섹션은 이어 붙인다.
그러면 군집 개선은 유지하면서 파편만 사라진다.

의미로 봐도 이쪽이 맞다. `3.1.3 로그인` 아래 `URL` / `Query parameters` / `Body` 는
같은 API 의 조각이라 한 청크에 있는 게 자연스럽다. 따로 떼면 파라미터 표만 맥락 없이 남는다.

h6 까지 넓히는 것은 **특정 문서에 맞추는 게 아니라 레벨 제한을 없애는 것**이다.
마크다운 헤더는 h1~h6 가 전부이므로, 전부 경계로 삼으면 "이 문서는 h5 를 쓴다" 같은
문서별 가정이 사라진다. h1~h3 로 자르던 쪽이 오히려 임의의 가정이었다.

함께 청크 `metadata` 를 바꿨다.

```python
# 전
{'h1': ..., 'h2': ..., 'h3': ..., 'page_number': n}
# 후
{'headings': ['4. System', '4.1 시스템 정보', '4.1.1 시스템 정보 조회', 'URL'],
 'page_number': n}
```

레벨이 6단계라 빈 키를 여섯 개 들고 다니는 게 낭비이고, 소비하는 쪽
(`SpecExtractor._as_context`)이 어차피 `' > '` 로 이어 붙여 쓴다.

## 결과

**좋아진 것**

- 청크가 서로 구분된다. 같은 헤더 경로를 공유하는 청크가 77% 줄었다.
- LLM 호출은 5%만 늘었다. 군집 개선을 거의 공짜로 얻었다.
- 청크 메타데이터에 API 이름(h5)과 요청/응답 구분(h6)이 실린다. 추출 프롬프트가
  `[문서 위치] 4. System > 4.1.1 시스템 정보 조회 > Query parameters` 를 앞에 달고 나간다.
- `headings` 가 리스트라 문서 구조가 더 깊어져도 계약이 안 깨진다.

**나빠진 것 / 감수하기로 한 것**

- **헤더 없는 청크가 1 → 18 개로 늘었다.** 문서당 1개꼴이고 전부 표지·서문이다.
  첫 헤더 이전 preamble 이 병합 묶음의 선두가 되면 경로가 빈다. 선별 단계가 걸러낸다.
- **병합된 청크의 헤더 경로는 묶음 첫 섹션의 것이다.** 뒤쪽 섹션의 경로는
  메타데이터에 안 남는다. 다만 헤더 줄 자체는 본문에 남아 있어서(`strip_headers` 를
  하지 않는다) LLM 은 읽을 수 있다.
- **청크 `metadata` 계약이 바뀌었다.** `h1`/`h2`/`h3` 키를 읽던 코드
  (`SpecExtractor`, `SpecRepository`, `FileParser`)를 함께 고쳤다. 외부 소비자는 없다.
- 목차의 점선 줄(`1. REST API 설정 ......`)도 헤더로 잡혀 섹션이 된다. 걸러내지 않았다 —
  선별 단계가 판단할 몫이고, 목차를 헤더로 오인해서 생기는 손해가 없다.
- **청크 15개(0.6%)가 `chunk_size` 를 +5 ~ +246자 넘는다.** 분할 자체는 상한을 지키는데,
  그 뒤에 표 컬럼 헤더를 다시 붙이면서 넘긴다. 헤더 없는 표 조각을 LLM 에 넘기는 것보다
  낫다고 판단했다. `chunk_size` 는 비용·정확도 조절값이지 하드 리밋이 아니다.

  같은 재부착에서 버그 두 개가 나와 함께 고쳤다 — 헤더가 자기 자신 위에 복제되던 것,
  그리고 변환기가 데이터 셀을 헤더 행으로 잡았을 때 청크가 1.6배로 부풀던 것.
  둘 다 인공 데이터 자체 점검으로는 안 잡히고 실제 문서에서만 드러났다.
  → [실험의 "반영 후 재검증"](../experiments/2026-08-06-header-level-and-chunk-merge.md)

**되돌려야 할 신호**

- 병합 때문에 서로 관계없는 섹션이 한 청크에 섞여 추출 정확도가 떨어지면,
  병합 조건에 "같은 부모 헤더를 공유할 때만" 을 추가한다.
- 헤더가 거의 없는 문서(변환기가 구조를 못 잡는 PDF)가 주류가 되면 헤더 기반 분할
  자체가 의미를 잃는다. 그때는 페이지 마커나 표 경계를 1차 기준으로 검토한다.
