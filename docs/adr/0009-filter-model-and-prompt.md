# ADR-0009: 선별에 비추론 모델과 영어 프롬프트를 쓴다

- **상태:** Accepted
- **날짜:** 2026-08-06

## 배경

선별(filtering)은 청크마다 LLM 을 부른다. 문서 18개에 청크가 2,504개이므로
**호출 수가 가장 많은 구간**이고, 모델과 프롬프트가 그대로 총비용이 된다.

[ADR-0007](0007-evidence-based-confidence-scoring.md) 에서 단계별로 모델을 나누기로
하면서 `openai_filter_model=gpt-5-nano`, `openai_extract_model=gpt-5-mini` 를 기본값으로
두었다. "선별은 판정이 참/거짓 하나뿐이니 싼 모델" 이라는 논리였는데, **짐작이었고
한 번도 돌려보지 않았다.**

실측하니 세 가지가 전부 틀렸다.
→ [실험](../experiments/2026-08-06-filter-model-selection.md)

## 선택지

**A. `gpt-5-nano` 유지.** 참/거짓 하나에 청크당 1,467 토큰을 쓴다. 대부분이 추론
토큰이다. 단가가 싸도 토큰을 20배 쓰면 총비용이 역전된다.

**B. `gpt-5-nano` + `reasoning_effort='minimal'`.** 210 토큰까지 줄지만 정밀도가 22% 로
무너진다 — 목차 다섯 개를 전부 "API 규격" 으로 판정했다. 추론으로 벌충하도록 훈련된
모델에서 추론을 빼앗으면 비추론 모델보다 나빠질 수 있다.

**C. `gpt-4.1-nano`.** 청크당 7 토큰, 정밀도 100%. 가장 싸고 가장 정확하다.
**다만 39청크 3회 실행에서 통과 개수가 22 / 25 / 26 으로 흔들린다.**
`temperature=0` 으로도 안 잡혔다.

**D. `gpt-4o-mini`.** 청크당 7 토큰, 정밀도 67%. 39청크 3회에서 30 / 30 / 30 으로 일치.

`gpt-4.5-preview` 는 API 에서 내려갔다(404).

## 결정

**D — `gpt-4o-mini`.** 정밀도가 C 보다 낮은데도 고른 이유는 **재현성** 때문이다.

판정이 실행마다 달라지면 같은 문서를 두 번 올렸을 때 적재되는 API 집합이 달라진다.
ADR-0007 에서 채점을 결정적으로 만들려고 LLM judge 를 피했는데, 정작 그 앞단이
흔들리면 파이프라인 전체의 재현성이 없다. C 의 정밀도 우위(과다 통과 1개 차이)는
추출 단계에서 걸러지는 비용이지만, 흔들림은 결과 자체를 바꾼다.

프롬프트는 영어로 바꿨다. 같은 내용인데 요청 토큰이 15% 줄어든다 — 한글이 GPT
토크나이저에서 글자당 1~2토큰이라, 청크마다 들어가는 이 단계에서 차이가 누적된다.
2,504청크 기준 약 20만 토큰이다.

프롬프트에서 **거짓 목록은 건드리지 않는다.** 그것만 뺀 변형이 정밀도 20% 로 무너졌다.
모델은 "무엇이 API 규격인가" 보다 "무엇이 아닌가" 를 듣고 판단한다.

`판단이 애매하면 참으로 둔다` 문구는 뺐다. 놓침을 막으려고 넣었는데 재현율이 어차피
전 모델 100% 라 막을 게 없었고, 과다 통과만 늘렸다.

## 결과

**좋아진 것**

- 선별 출력 토큰이 청크당 1,467 → 7 로 줄었다.
- 입력 토큰이 프롬프트 영어화로 15% 줄었다.
- 판정이 실행마다 뒤집히는 폭이 크게 줄었다.
- 실험 스크립트가 `SpecExtractor.FILTER_PROMPT` 를 직접 import 하므로, 프롬프트를
  고치면 재측정이 바로 된다. 사본을 두지 않았다.

**나빠진 것 / 감수하기로 한 것**

- **`gpt-4o-mini` 도 완전 결정적이지 않다.** 3회 일치는 봤지만 이후 실행에서 같은 조건이
  29/39 와 30/39 로 갈렸다. 흔들림 폭이 `gpt-4.1-nano`(22~26)와 비교가 안 될 뿐이다.
  같은 문서를 두 번 올리면 결과가 미세하게 다를 수 있다.
- **정밀도 67% 를 감수했다.** 과다 통과분은 추출 단계에서 근거를 못 만들어 걸러지지만,
  그만큼 추출 LLM 호출이 낭비된다.
- **선별 프롬프트만 영어다.** 추출과 대상 식별은 한국어로 남겼다 — 아직 실험하지 않은
  단계라 검증한 것만 바꾼다. 프롬프트 언어가 파일 안에서 섞인다.
- **정답 라벨이 10청크(참 2개)뿐이다.** 재현율 100% 라는 결과는 이 표본에서 놓칠 만한
  어려운 케이스가 없었다는 뜻일 수도 있다.
- 영어화 실험에서 언어와 거짓 목록 내용을 동시에 바꿔 원인이 섞였다. 둘 다 이득
  방향이라 채택에는 지장이 없지만, "영어라서 정확해졌다" 는 근거는 없다.

**룰 기반으로 대체하지 말 것**

정규식으로 하면 호출이 0 이 된다는 발상을 실측했다. SECUI MFD 39청크에서는 LLM 과
90% 일치했지만, 문서 18개로 넓히니 통과율이 0%~88% 로 요동쳤다.

**FortiOS 6.0 은 LLM 이 192개를 잡는데 룰은 33개만 잡는다(83% 놓침).** 이 문서는 표가
0개이고 산문으로 API 를 설명해서 룰이 볼 신호가 없다. 룰은 형식을 보고 LLM 은 의미를
본다 — 벤더마다 문서 스타일이 다른 이상 룰은 새 벤더가 올 때마다 깨진다.

하이브리드(룰 참이면 LLM 생략)도 호출을 52% 줄이지만 통과분 정밀도가 룰 수준(50%)이
된다. 추출이 선별보다 비싼 단계라 과다 통과 하나가 선별 호출 몇 개보다 손해다.

**더 줄이려 하지 말 것**

프롬프트가 한 요청의 20% 다 (71토큰 vs 청크 본문 281토큰). 0으로 만들어도 절감 상한이
20% 이므로, 문장을 더 압축해 봐야 3% 를 얻고 판정이 갈린다. 목차 정규식 사전필터도
4.3% 인데 놓침 위험을 새로 만든다.

한국어 → 영어 전환이 33% 를 가져갔고 그게 이 단계에서 딸 수 있는 가장 큰 열매였다.
다음으로 큰 것은 `chunk_size` 이지만(1000 → 2000 이면 프롬프트 반복이 절반) 그건
청킹 설계 변경이라 ADR-0008 의 군집·파편 지표를 다시 재야 한다.

**되돌려야 할 신호**

- 흔들림이 실제 문제로 드러나면(같은 문서 재업로드 시 결과 차이로 운영에 혼란) 판정을
  캐시한다 — 청크 텍스트 해시를 키로 두면 같은 청크는 항상 같은 답이 된다.
- 놓침이 발견되면 정답 라벨을 늘려 재측정한다. 라벨이 부족해서 못 본 것일 수 있다.
- 추출 단계를 실험한 뒤 프롬프트 언어를 통일한다.
