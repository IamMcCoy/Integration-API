# 채점이 엔드포인트를 안 보고 있었다

- **날짜:** 2026-08-06
- **결론:** 엔드포인트도 원문과 대조하고, 같은 API 의 조각을 적재 전에 합치고,
  `temperature=0` 을 준다. 3회 모두 적중이 13/24 에서 22/24 로 올랐다.
  `chunk_size` 는 1,000 을 유지한다 — 키우면 추출이 무너진다.

## 배경

[ADR-0008](../adr/0008-header-level-and-section-merge.md) 에서 청킹을 고치면서
"한 API 가 여러 청크로 쪼개지면 어떻게 되나" 를 재지 않았다. 재보니 API 단위 1,213개 중
**380개(31%)가 2청크 이상**에 걸쳐 있었고, `api_schema` 는 `UNIQUE(api_def_id)` 라
나중 추출이 앞의 것을 덮어쓴다. 파라미터가 조용히 사라지는 구조였다.

`chunk_size` 를 키우면 해결될 것 같았다. 청킹 지표는 전부 그 방향을 가리켰다.

| chunk_size | 청크 | 파편 | 상한초과 | 군집합 | 쪼개진 API |
|---|---|---|---|---|---|
| 1,000 | 2,504 | 68 | 15 | 278 | 380 |
| 4,000 | 517 | 1 | 0 | 64 | 51 |
| 8,000 | 242 | 0 | 0 | 36 | 16 |

## 방법

정답은 문서에서 기계적으로 뽑는다. `POST http(s)://[serverip]/mfd/api/token` 형태의
**메서드+경로는 API 마다 고유**하므로 사람 라벨링 없이 재현율을 잴 수 있다.
SECUI MFD 에서 24개가 나왔다.

`scripts/2026-08-06-extract-chunk-size.py`.

## 결과 1 — chunk_size 를 키우면 추출이 무너진다

| chunk_size | 청크 | 적중 (24개 중) | 파라미터 | 평균점수 |
|---|---|---|---|---|
| **1,000** | 39 | **19** | **198** | 82.6 |
| 1,500 | 23 | 19 | 149 | 84.1 |
| 2,000 | 16 | 15 | 108 | 87.0 |
| 4,000 | 7 | 13 | 82 | 71.3 |
| 8,000 | 4 | 13 | 63 | 98.1 |

**청킹 지표와 추출 정확도가 정반대로 움직인다.** `chunk_size=8000` 은 청킹 지표가
최고였는데 API 절반을 놓치고 파라미터를 68% 잃었다. 큰 청크에 API 가 여러 개 들어가면
모델이 일부만 뽑는다.

**8,000 의 평균점수 98.1 이 함정이다.** 점수가 가장 높은데 파라미터는 가장 적다 —
적게 뽑고 정확하게 뽑은 것이다. 채점은 뽑은 것만 검증하고 **안 뽑은 것을 벌하지 않으므로**,
점수만 보면 최악의 설정이 최고로 보인다.

500 도 재봤는데 오검(정답에 없는 엔드포인트)이 44개로 폭증했다. **1,000~1,500 이 최적
구간**이고, 현재값 1,000 을 유지한다.

이것으로 "쪼개지는 게 손해" 라는 전제도 뒤집혔다. 쪼개진 조각에서 각각 뽑은 파라미터를
다 합치면 198개인데, 안 쪼개고 통째로 뽑으면 63개다. **쪼개는 게 이득**이고, 문제는
조각을 합치지 않는 것이었다.

## 결과 2 — 채점이 엔드포인트를 안 보고 있었다

오검 13개를 열어 보니 전부 환각이었다.

```
GET  /acl/view          GET  /api/acl           POST /acl/add
GET  /api/protect-domain   GET /api/protectDomain   GET /api/protectedDomain
NONE None               NULL null
```

실제 경로는 `/mfd/api/policy/pdomains` 인데 모델이 "보호 도메인"이라는 한글 제목에서
그럴듯한 영문 경로를 **매번 다르게** 만들어냈다.

문제는 이것들이 **100점을 받아 자동 적재된다**는 점이다. `Parameter` 에는 `evidence`
필드가 있지만 `ApiSpec.endpoint` / `method` 에는 없다. [ADR-0007](../adr/0007-evidence-based-confidence-scoring.md)
의 채점은 파라미터만 검증하므로, 파라미터 근거가 맞으면 엔드포인트가 무엇이든 통과한다.

**더 치명적인 필드가 검증에서 빠져 있었다.** 파라미터가 틀리면 인자 하나가 잘못되지만,
엔드포인트가 틀리면 API 자체가 존재하지 않는다.

`NONE` / `null` 도 같은 구멍으로 들어온다. `_normalize_method('NONE')` 은 허용 목록에
없어서 NULL 로 떨어지지만, `endpoint = "None"` 은 아무 검사 없이 `VARCHAR(500)` 에 저장된다.

→ `SpecScorer.score` 에서 엔드포인트 경로가 원문에 없으면 **0점**으로 바꿨다.
환각 13개가 전부 걸러졌다.

## 결과 3 — 파라미터 없는 API 를 구조적으로 놓친다

놓친 API 가 일관되게 `PUT .../apply`, `PUT .../cancel` 계열이었다. 문서에는
`Path parameters None / Query parameters None / Body None` 으로 **명시**돼 있다.

두 곳에서 막고 있었다.

- 프롬프트: "조각에 API 규격이 없으면 specs 를 빈 배열로" → 파라미터가 없으면 규격이 아니라고 판단
- 채점: `if not parameters: return 0` → 뽑아도 0점

ADR-0007 에서 "파라미터가 없으면 이 파이프라인이 얻으려던 게 없다" 고 판단했는데,
실제 문서에는 인자 없는 액션 API 가 존재했다.

→ 프롬프트에 "파라미터가 없는 API 도 규격이다" 를 넣고, 채점은 엔드포인트에 근거가
있으면 100점을 주도록 바꿨다.

## 결과 4 — 조각을 적재 전에 합친다

같은 API 의 조각들을 병합했다. 병합 키는 **LLM 이 낸 `title` 이 아니라 청크의 헤더
경로**다 — 같은 API 라도 조각마다 `ACL 추가` / `ACL 추가 응답` 처럼 다르게 나오지만,
헤더 경로는 문서 구조에서 오므로 반드시 일치한다.

첫 시도에서 **API 2개를 잃었다.**

```
그룹 '4.3.2 ACL 추가'    →  POST /acls 와 PUT /acls/{id} 둘 다 있음
그룹 '5.2.4.1 ... 적용'  →  apply 와 cancel 둘 다 있음
```

문서가 `5.2.4 적용/취소` 처럼 한 헤더에 API 둘을 묶어 쓰는 경우가 있는데, 그룹당
엔드포인트를 하나만 고르니 나머지가 조용히 버려졌다. **정답 대조를 안 했으면
"반려가 줄었다" 는 지표만 보고 성공으로 착각했을 것이다.**

→ 그룹 안에서 **근거 있는 엔드포인트별로 다시 나눴다.** 엔드포인트를 못 찾은 조각은
어디 붙일지 알 수 없으므로 단독으로 둔다 — 잘못 붙이면 남의 파라미터가 섞인다.

| | 항목 | 적재 | 반려 | 적재 파라미터 | 적재 API |
|---|---|---|---|---|---|
| 병합 전 | 40 | 22 | 16 | 121 | 18 |
| 병합 후 | 28 | 20 | **6** | **127** | 18 |

반려 16 → 6 이 실질 개선이다. 줄어든 10개는 "URL 없는 조각이라 0점 맞던 것" 인데,
같은 API 의 URL 있는 조각과 합쳐져 근거를 얻었다.

## 결과 5 — 추출이 실행마다 흔들린다

세 수정을 넣고 3회 돌렸더니 이랬다.

```
회차   적재   파라미터   적중
  1     19       112    18/24
  2     24       148    21/24
  3     19       116    17/24

3회 모두 적중  13/24 (54%)
파라미터 편차   36 (32%)
```

**선별은 3회 모두 29개로 완전히 안정적인데 추출만 흔들린다.** 출력 복잡도 차이다 —
선별은 `bool` 하나지만 추출은 API 여러 개에 파라미터 수십 개를 뱉는다.

[ADR-0009](../adr/0009-filter-model-and-prompt.md) 에서 "`gpt-4o-mini` 는 temperature
무관하게 안정적" 이라고 썼는데, **그건 선별에 한정된 사실이었다.**

`temperature=0` 을 주고 다시 쟀다.

| | 적중 | 3회 모두 적중 | 파라미터 | 편차 |
|---|---|---|---|---|
| 기본 (1.0) | 20 / 20 / 20 | 16/24 | 122 / 138 / 120 | 18 |
| **0** | **23 / 23 / 24** | **23/24** | 158 / 160 / 162 | **4** |

**재현성만 오를 줄 알았는데 정확도도 같이 올랐다.** 낮은 temperature 가 "보수적이 되어
덜 뽑을" 것으로 예상했는데 반대였다 — 무작위성이 정답을 만들어내는 게 아니라
**정답에서 이탈시키고** 있었다.

## 최종

네 수정을 다 넣고 본 코드로 3회.

```
회차   적재   대기   반려   파라미터   적중
  1     25     1      3      147     23/24
  2     25     1      3      147     23/24     ← 1회차와 완전 동일
  3     24     2      3      156     22/24
```

| | 수정 전 | 수정 후 |
|---|---|---|
| 3회 모두 적중 | 13/24 (54%) | **22/24 (92%)** |
| 파라미터 편차 | 36 | **9** |
| 적재 파라미터 | 112~148 | **147~156** |
| 환각 엔드포인트 | 통과 | **13개 차단** |

**네 수정이 서로 맞물린다.** 엔드포인트 채점이 없었으면 병합이 환각 경로로 그룹을
쪼갰을 것이고, `temperature=0` 이 없었으면 병합해도 매번 다른 파라미터 집합이 합쳐졌을
것이다. 하나씩 고치며 매번 실측한 것이 순서를 잡아줬다.

→ [ADR-0010](../adr/0010-extraction-verification-and-merge.md)

## 남은 것

`PUT /mfd/api/policy/pdomains/{id}` 하나가 3회 모두 '적중' 집계에서 빠졌다. 나중에
엔드투엔드로 확인해 보니 **놓친 게 아니라 87점을 받아 승인 대기로 간 것**이었다 —
파라미터 15개 중 13개만 근거가 확인됐다. 이 실험의 '적중' 은 `score >= 90` 만 세므로
사람 승인 대기는 집계에서 빠진다. 설계대로 동작한 것이지 결함이 아니다.

**지표를 만들 때 파이프라인의 세 갈래(자동 적재 / 승인 대기 / 반려) 중 하나만 센 것이
실수였다.** 다음에 같은 측정을 할 때는 대기까지 포함해서 봐야 한다.

문서 하나(SECUI MFD, 39청크, 정답 24개)로만 쟀다. 표가 0개인 FortiOS 처럼 형식이 다른
문서에서 같은 결론이 나오는지는 확인하지 않았다.

## 재현

```bash
# 마크다운 캐시는 청킹 실험 스크립트가 만든 것을 쓴다
PYTHONPATH=. poetry run python scripts/2026-08-06-chunk-settings.py /tmp/mdcache /tmp/chunk.json

PYTHONPATH=. poetry run python scripts/2026-08-06-extract-chunk-size.py \
    '/tmp/mdcache/[SECUI] MFD REST API 가이드.md' 1000 4000 8000
```

정답은 스크립트가 문서에서 직접 뽑으므로 라벨 파일이 필요 없다. `data/` 는 gitignore 라
저장소에 없다 — 같은 벤더 문서를 넣고 돌려야 한다.

검증 환경: `openai 2.53.0`, `gpt-4o-mini`, SECUI MFD 39청크.
