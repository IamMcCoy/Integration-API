# 선별 단계에 추론 모델을 쓰면 참/거짓 하나에 1,045 토큰이 든다

- **날짜:** 2026-08-06
- **결론:** `gpt-4o-mini` + 영어 프롬프트. 추론 모델은 이 작업에 맞지 않고,
  프롬프트의 "거짓 목록" 이 정밀도를 좌우한다.

## 배경

선별(filtering)은 청크마다 LLM 을 부른다. 실측으로 문서 18개에 청크가 2,504개이므로
**호출 수가 가장 많은 구간**이고, 모델과 프롬프트 선택이 그대로 총비용이 된다.

그런데 기본값 `openai_filter_model=gpt-5-nano` 는 "싼 모델" 이라는 짐작으로 정한 값이고
한 번도 돌려본 적이 없었다. `chat.completions.parse` 시그니처가 맞는지조차 미검증이었다.

## 가설

1. 싼 모델(nano)이 비싼 모델(mini)보다 총비용이 낮다
2. 어느 모델이든 참/거짓 하나는 비슷하게 맞힌다
3. 판정은 같은 입력에 같은 답을 준다

## 방법

`scripts/2026-08-06-filter-models.py` 로 네 축을 잰다.

| 모드 | 내용 |
|---|---|
| `cost` | 모델 × `reasoning_effort` 별 토큰·지연 |
| `accuracy` | 사람이 매긴 정답 라벨과 대조 |
| `stability` | 같은 입력 3회, 판정이 흔들리는지 |
| `prompt` | 프롬프트 변형별 정확도·토큰 (모델 고정) |

정답 라벨은 SECUI MFD 문서의 첫 10청크를 직접 읽고 매겼다.

```
0     표지 (주소·저작권)                         거짓
1~5   목차 (점선과 쪽번호)                       거짓
6     1.2 HTTP PUT/DELETE 제한 — 전역 규칙        거짓 (경계)
7     2.1.1 GUI Token 발급 — GUI 메뉴 조작 안내   거짓
8     2.1.2 API Token 발급 — URL·POST·파라미터    참
9     2.1.3 API Token 조회 — URL·GET·파라미터     참
```

두 오류의 대가가 다르므로 **재현율을 먼저 본다.** 규격을 놓치면(false negative) 그 API 는
영영 적재되지 않고 아무도 모른다. 아닌 걸 통과시키면(false positive) 추출 단계에서
근거를 못 만들어 걸러지고 비용만 조금 더 쓴다.

## 결과 1 — 추론 모델은 참/거짓에 맞지 않는다

청크 10개, 선별 판정만.

| 모델 | effort | 출력 토큰 | 추론 토큰 | 초 |
|---|---|---|---|---|
| `gpt-5-nano` | 기본 | **14,673** | 14,464 | 25.5 |
| `gpt-5-nano` | `minimal` | 210 | 0 | 1.3 |
| `gpt-5-nano` | `low` | 2,322 | 2,112 | 8.6 |
| `gpt-5-mini` | 기본 | 2,900 | 2,688 | 6.1 |
| `gpt-4.1-nano` | — | **70** | 0 | 2.2 |
| `gpt-4o-mini` | — | 70 | 0 | 5.1 |

**가설 1이 틀렸다.** `gpt-5-nano` 가 참/거짓 하나에 청크당 1,467 토큰을 썼다.
단가가 5배 싸도 토큰을 20배 쓰면 총비용이 역전된다. 대부분이 추론 토큰이다.

`reasoning_effort='minimal'` 로 끄면 210 토큰까지 줄지만, 그럴 거면 처음부터
비추론 모델을 쓰는 게 맞다 — 4.x 계열은 같은 일에 70 토큰이다.

`gpt-4.5-preview` 는 404 다. API 에서 내려갔다.

## 결과 2 — 가장 싼 모델이 가장 정확했다

```
정답      . . . . . . . . O O
gpt-4.1-nano             . . . . . . . . O O   재현율 100%  정밀도 100%
gpt-4.1-mini             . . . . . . . . O O   재현율 100%  정밀도 100%
gpt-4o-mini              . . . . . . + . O O   재현율 100%  정밀도  67%
gpt-4o                   . . . . . . . . O O   재현율 100%  정밀도 100%
gpt-5-nano               . . . . . . + + O O   재현율 100%  정밀도  50%
gpt-5-nano/minimal       . + + + + + + + O O   재현율 100%  정밀도  22%
gpt-5-mini/minimal       . . . . . . + + O O   재현율 100%  정밀도  50%

O 맞게 통과   X 놓침(치명)   + 과다 통과(비용만)   . 맞게 제외
```

**가설 2도 틀렸다.** 정밀도가 22%에서 100%까지 갈린다.

주목할 것은 **전 모델 재현율 100%** 라는 점이다. 아무도 규격을 놓치지 않았다.
차이는 전부 "쓸데없는 걸 얼마나 통과시키나" 이므로, 모델 선택 기준은
재현율을 지키면서 과다를 줄이는 것이 된다.

`gpt-5-nano/minimal` 은 목차 다섯 개를 전부 "API 규격" 으로 판정했다.
추론으로 벌충하도록 훈련된 모델에서 추론을 빼앗으면 비추론 모델보다 나빠질 수 있다.

## 결과 3 — 판정이 실행마다 흔들린다

39청크를 3회씩 돌려 통과 개수와 불일치 청크를 셌다.

| 모델 | temperature | 1회 | 2회 | 3회 | 불일치 |
|---|---|---|---|---|---|
| `gpt-4.1-nano` | 기본 | 23 | 25 | 22 | **6** |
| `gpt-4.1-nano` | 0 | 25 | 25 | 26 | **3** |
| `gpt-4o-mini` | 기본 | 30 | 30 | 30 | 0 |
| `gpt-4o-mini` | 0 | 30 | 30 | 30 | 0 |

**가설 3이 틀렸다.** 이게 정확도보다 심각하다 — 같은 문서를 두 번 올리면 적재되는
API 집합이 달라진다. `SpecScorer` 를 결정적으로 만들려고 LLM judge 를 피했는데
(ADR-0007), 정작 앞단이 흔들리면 파이프라인 전체의 재현성이 없다.

`gpt-4.1-nano` 는 `temperature=0` 으로도 안 잡혔다. gpt-5 계열은 애초에
`temperature` 를 1.0 으로 고정해 조절할 수 없다.

**단, `gpt-4o-mini` 도 완전 결정적은 아니다.** 위 3회에서는 일치했지만 이후 프롬프트
비교 실행에서 같은 조건이 29/39 와 30/39 로 갈렸다. 흔들림 폭이 `gpt-4.1-nano`
(22~26) 와 비교가 안 될 뿐이다. 앞서 "ACL 삭제가 탈락했다" 며 놓침을 의심했던 것도
재판정하니 참으로 나왔다 — 그것도 이 흔들림이었다.

## 결과 4 — 프롬프트가 모델보다 영향이 크다

모델을 `gpt-4o-mini` 로 고정하고 프롬프트만 바꿨다.

| 변형 | 정밀도 | 39청크 입력 토큰 | 절감 |
|---|---|---|---|
| `current` (한국어, "애매하면 참" 포함) | 67% | 21,166 | — |
| `no-lean` (한국어, 그 문구 제거) | 100% | 19,294 | −8.8% |
| `positive-only` (거짓 목록 제거) | **20%** | 18,000 안팎 | — |
| `signal-based` (구체 신호 명시) | 50% | 22,000 안팎 | +7% |
| **`en` (영어)** | 67% | **17,929** | **−15.3%** |
| `en-terse` (영어 최소) | 50% | 16,720 | −21% |

**거짓 목록이 정밀도를 좌우한다.** 그것만 뺀 `positive-only` 가 목차 다섯 개를 전부
통과시켜 정밀도 20%로 무너졌다. 모델은 "무엇이 API 규격인가" 보다 "무엇이 아닌가" 를
듣고 판단한다. 그래서 `en-terse` 처럼 거짓 목록을 줄이는 방향은 손해다.

**"애매하면 참으로 둔다" 는 이득이 없었다.** 놓침을 막으려고 넣은 문구인데, 재현율이
어차피 전 모델 100% 라 막을 게 없었고 과다 통과만 늘렸다.

**영어가 토큰을 15% 줄인다.** `en` 은 글자 수가 한국어판의 1.4배(366자 vs 263자)인데
요청 토큰은 83개 적다. 한글이 GPT 토크나이저에서 글자당 1~2토큰이기 때문이다.
프롬프트는 청크마다 들어가므로 2,504청크 기준 약 20만 토큰 차이다.

**주의 — 이 실험은 원인이 섞였다.** `en` 은 언어만 바꾼 게 아니라 거짓 목록에
`GUI click-through instructions` 를 추가했다. `current` 가 통과시킨 청크 7(GUI 조작
안내)을 `en` 이 걸러낸 것은 그 항목 덕이지 영어라서가 아니다. 두 변화 모두 이득
방향이라 채택에는 지장이 없지만, "영어라서 정확해졌다" 고 읽으면 안 된다.

## 결과 5 — 프롬프트를 더 줄이는 것은 천장이 낮다

`en` 을 채택한 뒤 "더 줄일 수 있나" 를 따로 쟀다. `tiktoken` 으로 토큰을 직접 세면
구성이 이렇다.

```
프롬프트      71 토큰   (청크마다 반복)
청크 본문    281 토큰   (평균)
→ 한 요청에서 프롬프트 비중 20%
```

**프롬프트를 0으로 만들어도 절감 상한이 20%다.** 요청의 80%가 청크 본문이기 때문이다.

거짓 목록은 그대로 두고 문장만 압축한 변형을 39청크로 비교했다.

| 변형 | 글자 | 프롬프트 토큰 | 39청크 입력 | 절감 | `en` 대비 판정 차이 |
|---|---|---|---|---|---|
| `en` | 366 | 71 | 17,929 | — | — |
| `en-compact` | 261 | 57 | 17,383 | −3.0% | 1개 |
| `en-norole` | 300 | 60 | 17,500 | −2.4% | 1개 |
| `en-minimal` | 182 | 41 | — | — | 정밀도 40%로 하락 |

3% 절감에 판정이 1개 갈리는데, 그게 개선인지 악화인지 이 표본으로는 구분되지 않는다.
**`en` 을 유지했다** — 재검증 비용이 이득보다 크다.

LLM 호출 자체를 줄이는 쪽도 쟀다. 목차 줄(`\.{4,}\s*\d+$`)이 절반 이상인 청크를
정규식으로 미리 걸러내면 이렇다.

```
2,504청크 중 목차로 판정 153개 (6.1%)
절감 14,838 토큰 + 프롬프트 153 x 71 = 총 25,701 토큰 (전체의 4.3%)
```

이것도 4% 다. 목차 청크는 짧아서(평균 97토큰) 개수 비중에 비해 토큰 비중이 작다.
게다가 정규식이 진짜 규격을 오인하면 놓침이 생긴다 — 이 파이프라인에서 가장 비싼 오류다.

**정리하면 최적화 여지는 이미 대부분 소진됐다.**

| 수단 | 절감 | 비고 |
|---|---|---|
| 한국어 → 영어 | **33%** (프롬프트 106 → 71토큰) | 이미 적용 |
| 프롬프트 추가 압축 | 3% | 판정이 갈려 보류 |
| 목차 정규식 사전필터 | 4.3% | 놓침 위험을 새로 만든다 |
| `chunk_size` 1000 → 2000 | ~15% | 프롬프트 반복이 절반. 청킹 설계 변경이라 ADR-0008 재측정 필요 |

역설적으로 가장 효과적인 건 `chunk_size` 다. 프롬프트는 청크마다 반복되므로 청크 수가
절반이면 프롬프트 토큰도 절반이다. 다만 이건 프롬프트 최적화가 아니라 청킹 설계 변경이고,
군집·파편 지표가 같이 움직인다.

## 결과 6 — 룰 기반으로 LLM 을 대체할 수는 없다

"이 판정을 정규식으로 하면 호출이 0 이 되지 않나" 를 따로 쟀다.
`scripts/2026-08-06-rule-based-filter.py`.

룰은 네 가지 신호를 본다.

```python
HTTP_CALL     GET|POST|... 뒤에 경로나 URL          →  참
SPEC_SECTION  Path/Query parameters, Body, Returns  →  참
PARAM_TABLE   타입/필수 컬럼이 있는 표               →  참
TOC_LINE      점선 뒤 쪽번호가 절반 이상             →  거짓 (우선)
```

SECUI MFD 39청크에서는 잘 맞았다.

```
정답 10개 기준   LLM  재현율 100%  정밀도 67%
                룰   재현율 100%  정밀도 50%
39청크 일치율    90% (35/39)
```

갈린 4개 중 1개는 LLM 이 옳았고(GUI 조작 안내를 룰이 통과), 3개는 룰이 놓쳤다 —
전부 **표가 아닌 형태**의 파라미터 설명(불릿 목록, JSON 예시)이었다.

문서 18개로 넓히니 무너졌다.

| 문서 | 룰 통과율 |
|---|---|
| AhnLab TrusGuard | 88% |
| WAPPLES 5.0 | 81% |
| SECUI MF2 | 74% |
| **FortiOS 6.0** | **16%** |
| **TnD_MIBS** | **0%** |
| Webkeeper | 0% |
| 합계 | 52% (1,296 / 2,504) |

0% 두 건을 LLM 으로 확인했다.

```
TnD_MIBS           청크  51   LLM   0   룰   0    ← 일치
FortiOS 6.0        청크 202   LLM 192   룰  33    ← 룰이 159개(83%) 놓침
```

**TnD_MIBS 는 룰의 실패가 아니다.** 애초에 API 규격이 없는 문서였고 LLM 도 같은 판단을
했다. 반면 **FortiOS 는 재앙이다.** 이 문서는 표가 0개이고 산문으로 API 를 설명한다.
룰이 놓친 예:

```
###### Authentication Cookie
Authentication cookie (APSCOOKIE) is provided by the API after a successful
login request. All subsequent requests must ...
```

명백한 API 규격인데 표도 HTTP 메서드 표기도 없어 룰이 잡을 신호가 하나도 없다.

**룰은 형식을 보고 LLM 은 의미를 본다.** 벤더 18곳이 각자 다른 스타일로 쓰는 이상,
룰을 늘려 커버하려면 벤더마다 규칙을 추가하게 되고 새 벤더가 올 때마다 깨진다.

하이브리드(룰이 참이면 LLM 생략, 거짓이면 LLM 확인)도 검토했다. 호출은 52% 줄지만
통과분의 정밀도가 룰 수준(50%)으로 떨어진다. **추출은 선별보다 훨씬 비싼 단계**이므로
(구조화 출력에 근거 문자열까지 뱉는다) 과다 통과 하나가 선별 호출 몇 개보다 손해다.

**LLM 단독을 유지한다.**

## 결론

`gpt-4o-mini` + `en` 프롬프트를 채택했다. → [ADR-0009](../adr/0009-filter-model-and-prompt.md)

추출(`extracting`)과 대상 식별(`identify`) 프롬프트는 한국어로 남겼다. 아직 실험하지
않은 단계라, 검증한 것만 바꾼다.

## 재현

```bash
# 마크다운 캐시는 청킹 실험 스크립트가 만든 것을 그대로 쓴다
PYTHONPATH=. poetry run python scripts/2026-08-06-chunk-settings.py /tmp/mdcache /tmp/chunk.json

PYTHONPATH=. poetry run python scripts/2026-08-06-filter-models.py \
    '/tmp/mdcache/[SECUI] MFD REST API 가이드.md' all
```

모드를 `cost` / `accuracy` / `stability` / `prompt` 로 따로 줄 수 있다. 실행하면 지금
쓰는 `FILTER_PROMPT` 와 청크 하나가 실제로 넘어가는 모양을 먼저 찍는다 — 프롬프트는
`SpecExtractor` 에서 가져오므로 본 코드를 고치면 여기에도 반영된다.

`OPENAI_API_KEY` 가 필요하다. `.env` 에 넣어 두면 읽는다.

검증 환경: `openai 2.53.0`, 문서 SECUI MFD (39청크), 정답 라벨 10청크.
