# 헤더를 h3 까지만 자르면 청크가 어느 API 것인지 알 수 없다

- **날짜:** 2026-08-06
- **결론:** h1~h6 를 전부 경계로 삼되, 상한에 못 미치는 인접 섹션은 다시 이어 붙인다.
  청크 수는 +5% 인데 헤더 경로 중복은 77% 줄었다.

## 배경

`MarkdownChunker` 는 h1~h3 만 분할 경계로 썼다. langchain 의
`MarkdownHeaderTextSplitter` 예제를 그대로 옮긴 값이고, 실제 문서를 보고 정한 게 아니었다.

자체 점검은 통과했지만 그건 인공 데이터였다. `data/` 의 벤더 문서 18개로 처음 돌려봤다.

## 증상

SECUI MFD 문서(25K자)를 변환해 첫 청크를 보니 이런 게 있었다.

```
###### 문서 개정 이력

|문서버전|작성자|날짜|설명|
|---|---|---|---|
```

`######` — h6 다. 헤더 레벨 분포를 세어 보니 문서 구조가 이렇게 되어 있었다.

| 레벨 | 개수 | 내용 |
|---|---|---|
| h2 | 5 | `1. REST API 설정`, `4. System` — 대분류 |
| h3 | 16 | `4.1 시스템 정보` — 중분류 (+ 목차의 점선 줄) |
| h5 | 20 | `2.1.1 GUI Token 발급`, `4.1.1 시스템 정보 조회` — **개별 API** |
| h6 | 39 | `URL`, `Returns`, `Path parameters`, `Body` — **파라미터 구조** |

**우리가 필요한 정보가 전부 분할 기준 밖에 있었다.**

## 가설

1. 이 문서만 특이하다 → 확인 필요
2. h1~h6 를 전부 경계로 쓰면 청크가 잘게 쪼개져 LLM 호출이 폭증한다
3. 헤더는 전부 잡되 작은 섹션을 합치면 둘 다 얻는다

## 방법

18개 문서 전부에 세 설정을 나란히 돌렸다. 본 코드는 건드리지 않고 실험 스크립트 안에
분할 함수를 따로 구현했다.

| 설정 | 내용 |
|---|---|
| A | h1~h3 를 경계로 (당시 구현) |
| B | h1~h6 를 경계로 |
| C | h1~h6 를 경계로 + `chunk_size` 에 못 미치는 인접 섹션을 이어 붙임 |

측정 지표를 "청크가 몇 개 나오나" 가 아니라 **"청크가 서로 구분되나"** 로 잡았다.

- `worst_group` — 같은 헤더 경로를 공유하는 청크의 최대 개수.
  이게 크면 그만큼의 청크가 LLM 에게 똑같은 위치 정보로 보인다.
- `tiny` — 50자 미만 청크. 선별 단계가 청크마다 LLM 을 부르므로 곧 비용이다.
- `over` — `chunk_size` 초과. 크기 제어 실패.

`chunk_size=1000`, `chunk_overlap=200`.

## 해석

**가설 1은 틀렸다.** SECUI 만의 특성이 아니다. AhnLab 은 124,772자를 h1~h3 기준
7개 섹션으로 나눈다 — 섹션당 평균 18,000자다. 그 섹션이 크기 기준으로 20조각 넘게
잘리는데 20조각 전부 `h1='Chapter 2 REST API 목록'` 이라는 같은 메타데이터를 단다.
FortiOS 는 131,731자에 h1~h3 경계가 6개뿐이다.

**가설 2는 맞았다.** B 에서 50자 미만 청크가 59 → 765 로 13배가 됐다. 전체의 17% 다.
AhnLab TrusGuard 가 극단적인데, `###### 제품 버전`, `###### 일러두기` 같은 한 줄짜리
h6 가 340개 있어서 470청크 중 183개(39%)가 파편이 됐다.

의미로 봐도 손해다. `3.1.3 로그인` 아래 `URL` / `Query parameters` / `Body` 는 같은 API 의
조각이라, 따로 떼면 파라미터 표만 맥락 없이 남는다.

**가설 3이 맞았다.** C 는 A 대비 청크가 5% 늘 뿐인데 군집은 77% 줄었다.
B 보다 군집이 더 낮은 것(278 < 298)이 언뜻 역설로 보이지만, 병합은 *인접한* 작은 섹션만
합치므로 헤더 경로가 이미 다른 청크는 건드리지 않는다. B 에서 파편이던 것들이 사라지면서
같은 경로를 공유하던 군집이 정리된 것이다.

**감수한 것:** 헤더 없는 청크가 1 → 18 로 늘었다. 문서당 1개꼴이고 전부 표지·서문이다 —
첫 헤더 이전 preamble 이 병합 묶음의 선두가 되면 경로가 빈다. 선별 단계가 걸러낼
대상이라 실해가 없다고 판단했다.

## 반영 후 재검증에서 버그 두 개가 나왔다

실험 스크립트는 분할 로직만 옮겨 담았고 **표 헤더 재부착은 빼먹었다.** 그래서 C 를
`MarkdownChunker` 에 반영한 뒤 같은 18개 문서로 다시 돌려 대조했다.

```
총 청크 2,504   50자 미만 68   최대군집합 278     ← 실험과 완전히 일치
상한 초과 0 → 18                                  ← 불일치
```

초과한 18개가 전부 표로 시작하는 청크였다. 파고드니 둘 다 재부착 쪽 문제였다.

**버그 1 — 헤더가 자기 자신 위에 복제됐다.** 가장 긴 청크(2001자)를 뜯어보니 이랬다.

```
1행(표 헤더): 997자  |// Dynamic Nat {... JSON 예시 ...|
2행(구분선):    5자  |---|
3행(본문):    997자  |// Dynamic Nat {... 똑같은 내용 ...|
```

변환기가 JSON 예시 블록을 1컬럼 표로 인식해 셀 하나에 997자가 들어갔다. 셀이 상한보다
길어서 헤더 행과 구분선이 서로 다른 조각으로 갈라졌고, 헤더 행만 담긴 조각을 코드가
"구분선 없는 고아 조각" 으로 판정해 헤더를 또 붙였다.

자체 점검에서는 헤더가 짧아 항상 구분선과 같은 조각에 들어갔기 때문에 이 경로를 한 번도
밟지 않았다. **인공 데이터의 전형적인 한계다.**

→ 조각의 첫 줄이 헤더 행 자체와 같으면 붙이지 않도록 고쳤다.

**버그 2 — 재부착이 청크를 1.6배로 부풀렸다.** 남은 초과 청크를 `TextSplitter` 단계까지
역추적했다.

```
TextSplitter 결과:  [654, 932, 966, 996, 249, 5, 906, 994, 934]   ← 전부 상한 이하
최종 청크:          [611, 5, 996] = 1614자                        ← 611자 "헤더"가 붙음
```

분할은 정상이었고, 611자짜리 헤더 행이 붙어서 넘긴 것이다. 정상적인 컬럼명 줄은
`| 이름 | 타입 | 설명 |` 처럼 수십 자다. 611자는 변환기가 큰 데이터 셀을 헤더 행으로
잡은 것이고, 그걸 붙여 봐야 청크만 부풀고 얻는 정보가 없다.

→ 헤더 행이 `chunk_size` 의 절반을 넘으면 붙이지 않도록 가드를 뒀다.

**최종:** 상한 초과 15개 / 2,504개 (0.6%), 초과 폭 +5 ~ +246자.
표 헤더를 붙여서 조금 넘는 것이라 감수한다.

## 부수 확인

같은 실행에서 확인한 것들.

- **표 헤더 재부착이 실제 문서에서 작동한다.** SECUI MFD 에서 표로 시작하는 청크 7개,
  그중 구분선 없는 고아 조각 0개. (다만 위의 버그 두 개가 딸려 나왔다.)
- **분할 자체의 크기 제어는 완벽하다.** `TextSplitter` 단계에서 상한 초과 0개.
  최종 초과 15개는 전부 그 뒤에 붙는 표 헤더 때문이다.
- **페이지 번호가 단조증가한다.** 마커 잔존 0개.
- **FortiOS 두 판본은 표가 0개다.** 파라미터가 표가 아닌 형태로 적혀 있다는 뜻이라,
  추출 프롬프트가 표를 전제하면 안 된다.

## 결정

C 를 채택했다. → [ADR-0008](../adr/0008-header-level-and-section-merge.md)

`metadata` 를 `{h1, h2, h3, page_number}` 에서 `{headings: list[str], page_number}` 로
바꿨다. 레벨이 6단계라 빈 키를 여섯 개 들고 다니는 게 낭비이고, 소비하는 쪽
(`SpecExtractor._as_context`)이 어차피 `' > '` 로 이어 붙여 쓴다.

## 재현

```bash
poetry install
PYTHONPATH=. poetry run python docs/experiments/scripts/2026-08-06-chunk-settings.py \
    /tmp/mdcache /tmp/result.json
```

변환한 마크다운을 첫 인자 디렉토리에 캐시한다. PDF 18개 재파싱이 5분쯤 걸려서,
두 번째 실행부터는 캐시를 읽는다. `data/` 는 gitignore 라 저장소에 없다 —
같은 벤더 문서를 넣고 돌려야 한다.

스크립트에는 세 설정을 모두 남겨 뒀다. 지금 `MarkdownChunker` 는 C 뿐이라
본 코드를 import 하면 비교가 안 된다.

**스크립트 결과와 실제 코드는 다를 수 있다.** 스크립트에 표 헤더 재부착이 없어서
위의 버그 두 개가 여기서 안 잡혔다. 청킹을 고칠 때는 스크립트로 방향을 잡고,
반드시 `MarkdownChunker` 로 다시 돌려 대조할 것.

검증 환경: `opendataloader-pdf 2.5.0`, JVM 25, 문서 18개.
